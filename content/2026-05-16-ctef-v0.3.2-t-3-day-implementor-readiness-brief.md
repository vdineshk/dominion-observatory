## 1. Why this document exists

CTEF v0.3.2 — the Conformance Test & Evidence Framework — is on a public
publication path. The working-group draft includes §4.5 (behavioural
conformance attestation), and the version is scheduled to land on
**Monday 2026-05-19**. Once it publishes, two predictable things happen:

1. **Implementors searching for "CTEF §4.5 compliance", "CTEF readiness
   checklist", and "CTEF behavioural attestation reference" will find
   nothing they can act on.** Every search result will either predate v0.3.2
   or post-date it by a few hours. The first artifact that exists *before*
   publication and is *useful on publication day* becomes the canonical
   landing page by default.
2. **Standards-body chatter will fork between (a) implementors trying to
   self-attest and (b) registries deciding whether to ingest CTEF §4.5
   claims.** Both populations need the same readiness inputs. There is no
   neutral third party already publishing those inputs.

Dominion Observatory has been on the working-group reading list since

(EXP-035a, 2026-05-12, CC0-1.0). The next compounding move is the brief
you are reading — published **three days before** CTEF v0.3.2 lands, so

## 2. What CTEF v0.3.2 §4.5 introduces (working-group draft as of 2026-05-16)

This section summarises the *publicly-readable* portions of the draft. The
empire does not republish any non-public working-group material. If the
final published version diverges, this section will be corrected in-place
with a dated `[CORRECTION YYYY-MM-DD]` note.

| Surface | Working-group expectation | Implementor-side action on publication |
|---|---|---|
| §4.5.1 Behavioural attestation envelope | A canonical JSON envelope that wraps probe-side observations into a signed evidence record. The envelope is the unit a registry would ingest. | Implementors must decide whether to **self-attest** (sign their own envelope) or **be attested** (cite a third-party probe like Dominion Observatory). |
| §4.5.2 Conformance assertion vocabulary | A controlled vocabulary of conformance assertions (e.g., `latency_p95_under_threshold`, `success_rate_over_window`, `auth_required_for_protected_tool`). | Implementors need a checker that can run each assertion against their server and report pass/fail. |
| §4.5.3 Self-attestation discovery URI | A `.well-known/` URI carrying the implementor's most-recent self-attestation. Format is fixed in §4.5.3. | Implementors need to host a well-known endpoint matching the §4.5.3 schema. |
| §4.5.4 Cross-attestation field | An optional field in §4.5.1 envelopes that cites a third-party probe's most-recent independent observation. | Implementors who want stronger evidence cite a third-party probe; third-party probes (Observatory category) need a stable URI for the cited observation. |

## 3. Implementor readiness checklist (T-3 days)

For an MCP server operator who wants to be conformance-ready on Monday
2026-05-19, the four-question checklist is:

### Q1. Do you have a stable, public URL for your server?
- **Required for**: §4.5.1 envelope (the envelope wraps observations about a specific URL).
- **Empire-provided shortcut**: if your server is already tracked by the Observatory, your stable URL is your existing `tracked_since` row at `/api/leaderboard`. Search:
  `curl https://dominion-observatory.sgdata.workers.dev/api/leaderboard | grep <your-server-name>`
- **If not tracked**: register first.
  `POST https://dominion-observatory.sgdata.workers.dev/api/register` with `{"url":"https://your-server.example/mcp","name":"your-server"}`.

### Q2. Do you know your latency p95, success rate, and auth-required state?
- **Required for**: §4.5.2 conformance assertions.
- **Empire-provided shortcut**: `/api/trust/{server-slug-or-url}` returns the three numbers the spec needs. No setup required.
- **Caveat**: if your server's been tracked for <7 days, the success-rate observation is noisy. The empire's recommendation is to either (a) wait until a 7-day window has been observed before self-attesting, or (b) include the observation window length in your §4.5.1 envelope so consumers can weight accordingly.

### Q3. Are you planning to self-attest, be third-party-attested, or both?
- **Self-attest** (§4.5.3): you host `/.well-known/ctef-conformance` matching the §4.5.3 schema; consumers fetch it directly. Lowest external dependency, but consumers must trust you.
- **Third-party-attested** (§4.5.4): a probe like Dominion Observatory publishes the same observations at a stable URI; your §4.5.1 envelope cites that URI in the cross-attestation field. Higher external dependency, but consumers gain independent evidence.
- **Both**: industry-typical pattern. Self-attest for low-friction reads; cross-attest for high-stakes evidence.
- **Empire's recommendation**: for foundation-phase, do both. The combined cost is one well-known endpoint plus citing one cross-attestation URI.

### Q4. Have you scheduled the publication-day re-attestation?
- **Required for**: §4.5.1 envelope freshness (a self-attestation older than the spec's `max_age` is rejected by conformant consumers).
- **Working-group expectation**: §4.5.1 envelopes carry an `observed_at` timestamp; downstream consumers will configure `max_age` policies. A reasonable default is 7 days.
- **Empire's recommendation**: emit a fresh §4.5.1 envelope on publication day (Monday 2026-05-19) and again 7 days later (Monday 2026-05-26). After that, weekly is sufficient until §4.5 is widely adopted.

## 4. Decision tree for the three implementor classes

| Class | Recommended path | Empire endpoint to use | First action by Monday 2026-05-19 |
|---|---|---|---|
| **Server operator** (you run an MCP server, want to be CTEF §4.5-conformant) | Self-attest at §4.5.3 + cite Observatory at §4.5.4. | `/api/trust/{server}` for the assertion values, `/api/trust/verascore?subject={url}` for cross-attestation envelope. | Host `.well-known/ctef-conformance` matching the §4.5.3 schema. Empire-hosted reference implementation arriving 2026-05-19 (see Section 5). |
| **Registry / aggregator** (you ingest MCP servers, want to surface CTEF compliance) | Read §4.5.1 envelopes from server-operator `.well-known/` URIs. Cross-check against Observatory `/api/trust` for sanity. | `/api/leaderboard` for ecosystem-wide trust scores; `/api/agent-query/{server}` for per-server detail. | Define your §4.5.1 ingestion policy (which max-age, which trust score floor). |
| **Downstream agent** (you call MCP servers, want CTEF-attested ones) | Filter on §4.5.4 cross-attestations from probes you trust. | `/api/agent-query/{server}` returns the underlying observation set; the empire's behavioural telemetry is the cross-attestation. | Bookmark `/api/agent-query/{server}` for each MCP server your agent calls. |

## 6. What this brief is NOT

- **Not a normative specification.** CTEF v0.3.2 is the normative artifact;
  the empire is an implementor + a tracking authority, not the spec author.
  If anything in Sections 2-3 conflicts with the published v0.3.2, the
  published spec wins.
- **Not a vendor pitch.** Every empire-side endpoint cited in Section 4 is
  free, public, no-signup, and rate-limited only by Workers default.
- **Not a competitor scorecard.** Static directories (Glama, Smithery,
  mcp.so) operate on a different abstraction layer (registry hygiene, not
  behavioural attestation). The empire's positioning is behavioural
  cross-attestation — they are complements, not substitutes. A dedicated
  static-vs-behavioural comparison page is scheduled for publication day
  per CEO directive (2026-05-12).
